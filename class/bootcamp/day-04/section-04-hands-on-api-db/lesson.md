# 第 4 节 · 实战：用后端提示词生成 API 与数据库设计（35′ · 实战）

> 一句话：把 PRD、架构图和昨天的页面一起喂给后端 Agent，让它交出两张图纸——菜单和货架图。

## 教学目标

- 带读 `Backend_Engineer_Agent_Prompt.md` 两处关键段：OpenAPI 强制要求、数据库设计说明；
- 走通「先问澄清问题 → 列接口清单 → 逐个展开 → 配数据表」的生成流程；
- 产出 `API_Spec.md`（3–5 个接口）与 `DB_Schema.md`（2–3 张表）草稿。

## 讲授要点

### 提示词解剖：两处必看

打开 `Backend_Engineer_Agent_Prompt.md`，重点看两段：

1. **「API 定义文档（核心）」段**——「强制要求使用 OpenAPI 3.0 规范」。
   为什么是强制？因为这份文档的读者不只是人——前端 Agent、测试 Agent 都拿它当合同。
   同时注意它对每个接口的完整度要求：路径、方法、参数、请求体、**成功和错误响应都要 Schema**。
2. **「数据库设计说明」段**——列名、数据类型、约束（主键/外键/唯一/非空）、**索引建议**。
   注意「索引建议」四个字：这正是第 3 节说的——目录编在哪，是设计决策，AI 提建议，你来拍板。

### 生成流程（别一步到位的秘密）

直接说「给我设计后端」= 得到一份看似华丽、对不上你项目的模板货。正确节奏：

1. **先喂上下文**：PRD.md + architecture.md + 一句「页面已有 index.html，数据目前是写死的」；
2. **先让它问**：「动笔前，先问我 3 个澄清问题」——核心数据实体、谁调用这些接口、数据量级；
3. **先列清单再展开**：先要 3–5 个接口的一行清单（路径+方法+用途），你确认后再逐个展开成完整规格；
4. **表随接口走**：每展开一个接口，问一句「它读写哪张表」——对不上的，不是接口多设计了，就是表少设计了。

### 建议的 3–5 个接口（周报助手基线）

- `GET /reports?week=&dept=`——查周报列表；
- `POST /reports`——提交周报；
- `GET /reports/{id}`——看某一份详情；
- `GET /metrics/summary?week=`——驾驶舱卡片数据；
- （可选）`GET /users`——成员名单。

### 验收视角（生成后自查）

- 每个接口：路径 + 方法 + 成功响应 + 至少一个错误响应；
- 每张表：主键 + 列类型；全库至少一个索引建议；
- 接口 ↔ 表一一对应：指着一个接口，能说出它读写哪张表的哪几列。

## 🎬 口播稿（约 2.5 分钟）

【开场抛问】同学们，工具齐了——PRD、架构图、页面都在你手里。现在直接跟 AI 说「给我设计后端」，会发生什么？——一份漂亮但不对题的模板货。

【解剖】先看后端提示词两处硬规定。第一处：API 文档「强制」用 OpenAPI 格式——因为它的读者不只是你，前端、测试都拿它签合同。第二处：数据库设计必须带「索引建议」——目录编在哪，AI 提建议，你拍板。

【流程】正确节奏四步。第一，「喂上下文」——PRD、架构、页面一起给它。第二，「让它先问」——动笔前先问你三个澄清问题：核心数据是什么、谁来调接口、数据量多大。第三，「先清单后展开」——先要接口一行清单，你点头再逐个写全。第四——「表随接口走」。

【重点加高】第四步最关键。每展开一个接口就问：它读写哪张表？「对不上的」，不是接口多了，就是表少了。

【带走的话】记住——好设计不是一次生成的，是「问出来」的。你先当产品经理，AI 才是后端。

## 常见懵点（导师备用）

- 「AI 给的接口比我需要的多，要删吗？」→ 删。图纸上的每一道菜都要有人点；多出来的接口是未来的维护债；
- 「AI 没用 OpenAPI 格式输出怎么办？」→ 改约束重生成：「按 OpenAPI 3.0 YAML 输出 API_Spec.md」——不手改产物；
- 「错误响应 AI 只写了 200 怎么办？」→ 追问：「每个接口补上 400 与 404 的场景与响应体」——错误响应是契约的牙齿，不许缺。
