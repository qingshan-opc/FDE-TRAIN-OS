# 第 2 节 · API 设计：餐厅点菜模型与 OpenAPI（20′ · 概念）

> 一句话：API 就是菜单——菜名、做法要求、上错菜怎么办，三样写全才算一份能签合同的菜单。

## 教学目标

- 用点菜模型拆解一个 API 的三要素：菜名（路径）、做法要求（请求参数）、上错菜怎么办（错误码）；
- 一句话说清 REST：用 URL 表示东西、用动词（GET/POST/PUT/DELETE）表示动作；
- 理解 400/404/500 三个最常见错误码各自的含义与「锅是谁的」；
- 一句话说清 OpenAPI：把菜单写成机器也能读的格式，前后端靠它签合同。

## 讲授要点

### 一个接口 = 一次点菜

以「部门周报助手」的「查看本周已交名单」为例：

| 点菜 | API | 本例 |
|------|-----|------|
| 菜名 | 路径（Path）+ 方法 | `GET /reports` |
| 做法要求 | 请求参数 | `?week=2026-W30&dept=平台部` |
| 上菜 | 成功响应 | `200 OK` + 一份 JSON 名单 |
| 上错菜怎么办 | 错误响应 | `400` 参数写错 / `404` 没这周的记录 / `500` 后厨自己着火 |

### REST 一句话

REST 是业界最主流的 API 风格，记住一句：**URL 表示「东西」，动词表示「动作」**。
`/reports` 是「东西」（周报集合）；GET 拿来、POST 新交、PUT 改、DELETE 删。
错误示范：`/getReports`——动作写进了 URL，等于菜单上写「来点一个菜叫点鱼香肉丝」。

### 错误码：上错菜时的话术

- `400 Bad Request`——你单子填错了（缺参数、格式不对）：锅在点菜的人；
- `404 Not Found`——你要的东西后厨没有：东西不存在；
- `500 Internal Server Error`——后厨自己着火了：锅在餐厅。
  设计接口时只写「成功长什么样」是半成品，**错误响应才是契约的牙齿**。

### OpenAPI：机器也能读的菜单

OpenAPI（旧名 Swagger）是一套行业标准格式——用 YAML/JSON 把上面这张菜单写成机器可读的「合同」。
前端照它开发、后端照它实现、测试照它验收——**三方签的是同一份合同**，谁违约一目了然。
今天你要解剖的后端提示词里，OpenAPI 是「强制要求」，原因就在这。

## 🎬 口播稿（约 3 分钟）

【开场抛问】同学们，前后端隔着一堵墙，唯一的对话通道是 API。那——一份合格的 API 设计，要回答哪几个问题？

【类比】还回餐厅。一份合格的菜单回答三个问题：菜叫什么名字？能不能提要求——少辣、不要香菜？上错菜了怎么办？

【三要素】API 一模一样。菜名就是「路径」——比如 `GET /reports`，斜杠后面是你想要的东西。做法要求就是「请求参数」——哪一周、哪个部门。上错菜怎么办，就是「错误码」。

【错误码】记住三个数：「400」——你单子填错了，锅在你；「404」——你要的东西后厨没有；「500」——后厨自己着火了，锅在餐厅。只设计成功、不设计失败的菜单，是半成品。

【REST】行业里管这套风格叫 REST——人话一句：「URL 表示东西，动词表示动作」。东西是 `/reports`，动作是拿来、新交、改、删——GET、POST、PUT、DELETE。

【OpenAPI】最后，把菜单写成机器也读得懂的格式，叫「OpenAPI」——前后端拿它签合同，谁违约一目了然。

【带走的话】记住——设计接口，先想「上错菜怎么办」，再想「上什么菜」。

## 常见懵点（导师备用）

- 「GET 和 POST 不都能传数据吗？」→ 语义不同：GET 是「拿东西」不该改动数据，POST 是「交东西」会新增；语义对了，缓存、重试等机制才能正常工作；
- 「错误码有必要设计吗？出错返回个『失败』不就行了？」→ 「失败」两个字没法定位锅在哪；错误码是给排查问题的人留的路标；
- 「OpenAPI 和 API 什么关系？」→ API 是菜本身，OpenAPI 是菜单的标准排版格式——菜没变，但机器能读了。
