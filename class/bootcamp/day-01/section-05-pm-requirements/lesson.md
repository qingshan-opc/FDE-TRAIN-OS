# 第 5 节 · 指挥产品经理逐题确认需求（25′ · 对话实操）

> 一句话节引言：AI 可以整理需求，但真实问题、第一版范围和“确认需求”的责任属于学员。

## 教学目标

- 切换 `@产品经理` 并交付 `PROJECT_BRIEF.md`；
- 完成“一次一问 → 回答 → 复述确认”的需求澄清；
- 通过需求确认闸，生成正式 `PRD.md`。

## 产品经理对话阶段

1. 读取项目卡，不生成文档；
2. 逐题确认用户、流程、问题、数据、操作、平台、范围和验收；
3. 输出一页《需求确认摘要》；
4. 学员本人回复“确认需求”；
5. 生成 `PRD.md`；
6. 明确下一岗位和交接文件。

## PRD 最小结构

- 项目背景和目标用户；
- 当前流程与核心问题；
- 用户主要操作流程；
- 第一版功能与不做清单；
- 数据来源和页面清单；
- 用户故事与可衡量验收标准；
- 隐私和业务限制。

## 🎬 口播稿（约 11 段 · 定稿）

> 同学们，现在正式开始第一次岗位协作。请先确认工作区有 `PROJECT_BRIEF.md`，然后在 TRAE 对话框切换到 `@产品经理`。注意，不是继续跟通用 Agent 聊，也不是把六个岗位同时喊出来。当前只有产品经理开工，它的上游材料就是你刚刚写的项目卡。
>
> 传统产品经理会做访谈、会议、纪要和长文档整理，很多时间花在把不同人的说法汇总到一个版本。AI 时代的产品经理可以快速完成整理，但它更重要的职责是逐步暴露模糊点、帮助你做取舍，并把验收标准提前写清。你要观察的不是它写得多快，而是它有没有先问清楚再动笔。
>
> 第一段只介绍你的专业领域和项目卡，并明确说“现在不要生成 PRD”。要求产品经理一次只问一个问题，每题给一个回答示例。为什么一次一个？因为小白同时看到八个问题时，容易随便填完；一次一个，你可以认真思考，产品经理也能根据上一个答案继续追问。
>
> 每次回答后，产品经理应该先复述。例如你说“系统给招聘负责人使用”，它可以复述：“我理解主要用户是一线招聘负责人，不是所有员工，对吗？”你确认后才进入下一题。这个复述动作看起来慢，却是在消除未来返工。发现理解不对，当场改一句，比 UI 做完三张页面后重来便宜得多。
>
> 产品经理至少要问清八类内容：用户是谁，现在怎么做，哪一步最痛，数据从哪里来，用户需要完成哪些操作，主要在哪个设备使用，第一版做到哪里，以及什么结果算成功。它可能根据你的领域换一种问法，但不能跳过范围和验收。缺少这两项，AI 很容易把第一版做成一个没有边界的大平台。
>
> 回答时尽量给可判断的信息。不要只说“界面要方便”，可以说“招聘负责人打开首页十秒内能看到所有超期岗位”；不要只说“数据要准确”，可以说“页面中的岗位数量要与演示数据逐条一致”。验收标准不是为了为难开发，而是让后面的 UI、前端和测试都知道终点在哪里。
>
> 问题结束后，不要马上让它生成正式文档。先要求一页《需求确认摘要》，只包含用户、问题、流程、页面、数据、必须做、不做和验收标准。你要逐条读一遍。发现 AI 加入了你没说过的预测、自动发送或复杂权限，就明确删掉；发现漏掉关键规则，就在这里补充。
>
> 只有当摘要完全符合你的业务判断，才由你本人回复“确认需求”。这不是一句礼貌用语，而是一道责任闸。AI 负责整理，你负责确认。以后项目做偏了，我们可以回到这份确认记录追查：是产品经理擅自增加了内容，还是学员已经确认但后来改变了想法。
>
> 确认后让产品经理生成并保存 `PRD.md`。打开文件检查，不要只相信对话里的“已经完成”。确认里面有目标用户、核心问题、主要流程、第一版功能、不做清单、数据来源、页面清单和验收标准。再随机挑一条功能问自己：UI 看完以后，还需不需要回来猜它给谁用、怎样算完成？如果还要猜，继续回产品经理补清楚。
>
> 最后让产品经理写明交接语：“下一岗位是 UI，需要读取 `PRD.md`。”这一句话让你知道当前一棒已经结束。今天我们不会让产品经理自动调用 UI，而是由你亲自切换。交接前，产品经理必须把事实写进文件；交接后，UI 必须先读取并复述，不能凭想象开工。
>
> 带走一句话：AI 能帮你写需求，但不能替你确认需求。一个成熟的项目不是从“帮我做个系统”开始，而是从逐题澄清、范围取舍和人工确认开始。下一节，我们把 `PRD.md` 交给 UI，生成第一个可点击原型，然后再回到产品经理验收。

## 常见懵点（导师备用）

- “产品经理直接写 PRD 了” → 停止并重新要求一次只问一题，未确认不生成；
- “不知道怎么写验收标准” → 使用时间、数量、状态、是否出现或是否一致等可判断条件；
- “AI 加了很多高级功能” → 回到第一版范围，删除未确认内容并重新生成完整 PRD。
