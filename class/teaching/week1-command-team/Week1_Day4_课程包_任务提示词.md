## D4-L1 · 测试用例：从验收标准倒推

**使用方式**：Trae 对话中 **@测试工程师**。

**学员指令**：

```text
@测试工程师 请阅读 docs/PRD.md 的验收标准章和当前项目，把每条验收标准展开成可执行的测试用例，保存为 docs/D4-L1_测试用例表.md。要求：至少 10 条；覆盖正常、边界、异常三类；每条含前置条件、操作步骤、预期结果。其中至少包含 1 条驾驶舱看板数据核对用例（看板统计数字与列表页真实数据逐一核对）。
```

**教学要点**：用例不是拍脑袋想的，是从验收标准**倒推**的——D1 写验收标准时，就已经在决定 D4 怎么测。质量不是测出来的，是定义出来的。

**平台自检清单**：
- [ ] 用例 ≥10 条，正常/边界/异常三类都有
- [ ] 含看板数据核对用例（看板数字 vs 列表真实数据）
- [ ] 每条我能照着步骤操作并判断对错（可执行）
- [ ] 每条用例能追到 PRD 里对应的验收标准
- [ ] 我抽查了 2 条，发现"预期结果"写得清楚不含糊

**纠偏指令库**：

| 问题 | 指令示例 |
|---|---|
| 用例写得太笼统 | "这条用例的预期结果是'正常显示'——请改写成可判断对错的具体描述。" |
| 全是正常场景 | "现在全是顺利的情况，请补充边界（如金额为 0）和异常（如必填留空）用例。" |

## D4-L2 · 执行测试与缺陷报告

**使用方式**：学员**亲自执行**用例（不让智能体代劳），@测试工程师 协助整理报告。

**学员指令**：

```text
@测试工程师 我刚按 docs/D4-L1_测试用例表.md 执行完测试。以下是我发现的问题（附操作步骤和现象），请帮我整理成规范的缺陷报告 docs/D4-L2_缺陷报告.md：每条含重现步骤、预期结果、实际结果、严重程度分级（阻塞/严重/一般），并按你的经验帮我复核分级是否合理。
（粘贴你记录的问题；至少发现 2 条真实缺陷——认真按边界和异常用例测，一定能找到）
```

**教学要点**：**测试必须学员亲手跑**——智能体说"没问题"不算数，你点过才算数（验收权在你）。好缺陷报告 = 重现步骤 + 证据，"有时候不行"是最没用的报告。

**平台自检清单**：
- [ ] 用例执行结果矩阵完整（每条用例标了通过/失败）
- [ ] ≥2 条真实缺陷，每条含步骤/预期/实际/分级
- [ ] 我复核了智能体的分级建议，有 1 条我提出了不同意见或补充
- [ ] 没有"偶尔不行"这种无法重现的描述

**纠偏指令库**：

| 问题 | 指令示例 |
|---|---|
| 缺陷报告缺重现步骤 | "这条缺陷没有重现步骤，开发没法修——请按'从哪个页面、点什么、输入什么'补全。" |
| 分级明显不合理 | "提交按钮点了没反应是阻塞级，不是一般级——请说明你的分级依据。" |

## D4-L3 · 指挥修复：给工程师下修复单

**使用方式**：Trae 对话中 **@前端工程师** 或 **@后端工程师**（按缺陷归属）。

**学员指令**（每条修复单按此句式，学员自己组织）：

```text
@后端工程师 修复缺陷【缺陷标题】：
- 现象：……（从缺陷报告复制）
- 重现步骤：……
- 修复要求：……（改成什么样）
- 验收口径：修复后我重新执行用例【用例编号】应通过，且用例【相关用例编号】不得失效。
修复后告诉我改了哪里、为什么。
```

**教学要点**：修复单也要带验收口径；改 A 破 B 叫回归——所以修复后不只重测这一条，还要重测它旁边的用例。

**平台自检清单**：
- [ ] 修复单含现象/步骤/要求/验收口径四要素
- [ ] 修复后我重测了该用例并通过
- [ ] 我重测了至少 1 条相关用例（回归意识）
- [ ] 我能说清这个 Bug 的根因（智能体解释了，我听懂了）
- [ ] Git 有修复提交

**纠偏指令库**：

| 问题 | 指令示例 |
|---|---|
| 修好了 A 弄坏了 B | "修复后提交页正常了，但列表页状态显示错了——请检查这次修改影响了哪些地方。" |
| 智能体说"修好了"没解释 | "请说明这个 Bug 的根本原因是什么，你改了哪个文件哪段逻辑。" |

## D4-L4 · 验收清单与功能冻结

**使用方式**：Trae 对话中 **@测试工程师**。

**学员指令**：

```text
@测试工程师 参考企业项目验收的四个层次（做出来/用起来/有效果/能维护），为我的项目生成验收清单 docs/D4-L4_验收清单.md，覆盖功能、数据、异常、文档四类，每项标注证据链接。数据类必须包含一项：驾驶舱看板的每个统计数字都能与列表页真实记录核对一致。然后和我一起逐项核对打勾，未通过的写明原因和补救计划。
```

**学员指令②（冻结）**：

```text
我宣布：本项目从现在起进入功能冻结——不再加任何新功能，只修缺陷。请帮我检查最近代码提交，确认冻结生效，并在 README 顶部标注"状态：V0.9 功能冻结"。
```

**教学要点**：白皮书附录 F 的 mini 版实战——验收四层次（做出来/用起来/有效果/能维护）；冻结的意义：**范围感就是专业感**，敢说"不加了"的人才配交付。

**平台自检清单**：
- [ ] 验收清单四类齐全，每项有证据链接
- [ ] 未通过项有原因和补救计划（不是隐瞒）
- [ ] README 有冻结标注
- [ ] 冻结后没有新功能提交（我看 Git 日志验证过）

## D4-L5 · 今日冲刺：V0.9 与报审材料

**使用方式**：Trae **通用对话**。

**学员指令**：

```text
请帮我完成今日收尾：
1. 整理 Week 1 报审材料清单 docs/D4_报审材料清单.md：PRD、交互原型、前端页面、数据库与接口、测试用例表、缺陷与修复记录、验收清单——逐项检查文件是否真实存在、内容是否最新。
2. 为当前代码打 Git tag：v0.9。
3. 更新 README 当前进度为"Day 4 完成：测试与冻结 V0.9"。
```

**教学要点**：报审材料 = 明天综合验收的证据包。FDE 的验收从来不是"你看能跑"，而是"这是证据链"。

**平台自检清单**：
- [ ] 七项材料全部真实存在且内容最新
- [ ] Git tag v0.9 已打
- [ ] README 进度更新
- [ ] 我能用一分钟说清：这个系统现在能干什么、还有什么缺陷

## 附：平台侧配置提醒（内容团队）

1. **D4-L2 的"亲手测"是红线**：平台验收该节时要求提交"用例执行结果矩阵"，智能体代为执行的提交无效（抽检对话记录）。
2. **缺陷真实性**：学员编造假缺陷会被语义检查识别（缺陷描述与项目实际功能不符）——引导话术："认真跑边界和异常用例，一定能找到真 Bug；找不到真 Bug 的项目才可疑。"
3. **AI 导师 FAQ（D4 新增）**：学员说"我的项目没 Bug"（→ 引导跑异常用例）；学员不知道缺陷归前端还是后端（→ 分段定位法，复用 D3 联调指令）；冻结后学员想加功能（→ "记下来，写进 PRD 的 Backlog——冻结不是删除，是排期"）。
4. 预估 D4 卡点 Top 3：用例不可执行（预期结果含糊）、缺陷无法重现、冻结概念不理解（觉得"不继续加功能是吃亏"）。
