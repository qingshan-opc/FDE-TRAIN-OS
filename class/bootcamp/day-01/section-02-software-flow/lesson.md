# 第 2 节 · 软件项目怎么来的：六岗位、交接物与完整流程（15′ · 概念+流程图）

> 一句话节引言：软件不是某个人一句话“做出来”的，而是六个岗位拿着明确交接物完成的一场接力。

## 教学目标

- 按顺序说出产品经理、UI、前端、后端、测试、运维六个岗位；
- 理解每个岗位“传统职能 vs AI 时代职能”的变化；
- 说清每个岗位接收什么、交付什么、下一步交给谁。

## 完整开发流程

```text
专业领域问题
→ 产品经理确认需求
→ UI 设计交互
→ 前端实现页面
→ 后端接入数据与业务规则
→ 测试检查并组织复测
→ 运维部署上线
→ 产品经理按最初需求做最终业务验收
```

## 六岗位：传统职能 vs AI 时代

| 岗位 | 传统职能 | AI 时代职能 | 主要交付物 |
|---|---|---|---|
| 产品经理 | 调研、整理需求、手写大量文档、跟进沟通 | 定方向、做取舍、确认范围、制定验收标准、验收 AI 产物 | `PRD.md` |
| UI | 手动画线框、逐页做视觉稿、反复调整组件 | 定信息层级与交互原则、给 AI 设计约束、检查原型是否可用 | `design-spec.md`、`ui-flow.md`、原型 |
| 前端 | 手写页面结构、样式和大量重复交互代码 | 选择实现方案、约束 AI 生成代码、检查还原度、状态与可维护性 | 正式前端、`frontend-api-needs.md` |
| 后端 | 手写接口、数据库操作和业务代码 | 设计系统边界、接口契约和数据模型，监督 AI 实现与安全 | `architecture.md`、API、数据库、服务 |
| 测试 | 人工重复点击、手写大量用例、逐项回归 | 设计风险和验收覆盖，让 AI 执行重复测试，核对证据与边界 | `test-plan.md`、`test-report.md` |
| 运维 | 手工装环境、发版本、盯服务器、故障救火 | 设计自动化部署、监控、备份和回退，审批高风险变更 | `DEPLOYMENT.md`、运行地址 |

## 岗位交接表

| 当前岗位 | 接收 | 交付给下一岗位 |
|---|---|---|
| 产品经理 | 学员的领域问题 | 给 UI：确认后的 `PRD.md` |
| UI | `PRD.md` | 给前端：设计规范、交互流程、原型 |
| 前端 | PRD、设计和原型 | 给后端：正式页面、数据和接口需求 |
| 后端 | PRD、前端数据需求 | 给测试：可运行系统、接口和运行说明 |
| 测试 | PRD、完整系统 | 不通过退回责任岗位；通过后给运维测试报告 |
| 运维 | 通过测试的系统 | 给产品经理：上线地址、运行与回退说明 |

## 🎬 口播稿（约 12 段 · 定稿）

> 同学们，上一节我们确定了一件事：你不用先会写代码，但你必须知道怎样指挥。那指挥的前提是什么？脑子里要有地图。今天这张地图不是某个工具的按钮，而是一套软件从问题到上线的完整工程流程。以后你换 TRAE、Codex、Cursor 或其他工具，按钮会变，模型会变，但这条接力链不会凭空消失。
>
> 先看全景：专业领域里出现一个真实问题，产品经理把它确认成需求，UI 把需求变成页面和操作流程，前端把设计变成正式页面，后端接入数据和业务规则，测试按标准找问题，运维把通过测试的系统部署上线，最后产品经理回到最初需求做业务验收。请注意最后还会回到产品经理，因为项目不是“上线了”就算成功，而是要确认它有没有解决最开始的问题。
>
> 第一棒是产品经理。传统产品经理经常花大量时间做访谈纪要、写长文档、排需求表、追着各方确认。AI 时代，这些文字整理工作可以被快速生成，产品经理的价值就向上移动：决定什么问题值得做、第一版做到哪里、什么坚决不做，以及怎样算合格。AI 能写 PRD，但“确认需求”这四个字必须由人负责。它的交付物是 `PRD.md`，下一棒交给 UI。
>
> 第二棒是 UI，也可以理解为 UI/UX 设计师。传统 UI 需要手动画线框、逐页做视觉稿、调颜色、调间距、反复摆组件。AI 时代，页面草稿可以几分钟生成，UI 的核心变成定义信息层级和交互原则：用户第一眼先看什么，最常用按钮放哪里，空数据、加载中、出错时怎样表现。UI 不是“让页面好看”的装饰岗位，而是把需求变成用户能理解的操作。它交付设计规范、交互流程和原型给前端。
>
> 第三棒是前端。传统前端大量时间花在手写页面结构、样式和重复交互代码。AI 时代，生成代码的速度变快了，但前端仍然要选择合适的实现方式，检查页面是否忠实还原设计，按钮状态是否完整，手机和电脑是否都能用，代码以后能不能继续维护。前端不应该凭空猜后端会返回什么，所以它还要交出一份数据需求清单，告诉后端哪个页面需要哪些字段。
>
> 第四棒是后端。传统后端会亲手写大量接口、数据库查询和业务代码。AI 时代，重复代码可以交给 AI，后端的价值更集中在系统边界、接口契约、数据模型、安全和稳定性。它要回答：数据存在哪里，谁能访问，前端通过什么接口读取，外部服务失败时怎么降级。我们目前没有单独设置架构师智能体，所以基础架构设计归入后端岗位。它交付可运行服务、接口说明、数据库设计和运行手册给测试。
>
> 第五棒是测试。传统测试常被误解成拿鼠标不停点击，其实过去确实有大量重复执行和回归工作。AI 时代，重复测试可以自动跑，测试岗位更重要的能力是设计覆盖：最危险的地方在哪里，正常流程之外有哪些边界，证据够不够说明问题，修复后是否真的没有复发。测试不应该偷偷替开发修改代码，而要写清复现步骤、预期结果、实际结果和责任岗位。失败就退回前端或后端，修好后再复测。
>
> 第六棒是运维。传统运维经常手工安装环境、发布版本、守着服务器，出故障时临时救火。AI 时代，部署命令和监控配置可以大量自动生成，运维更关注自动化、可观察、备份、回退和高风险操作审批。系统不仅要能启动，还要知道怎么停止、怎么更新、日志在哪里、坏了怎样恢复。运维交付上线地址和部署说明，然后把项目交回产品经理做最终业务验收。
>
> 现在我们把六棒连起来。产品经理给 UI 的不是一句“做漂亮点”，而是确认后的 PRD；UI 给前端的不是一张无法解释的图片，而是设计规范、交互流程和原型；前端给后端的不是一句“你看着给数据”，而是字段和接口需求；后端给测试的不是一句“应该能跑”，而是可运行系统和运行说明；测试给运维的不是一句“差不多了”，而是一份通过的测试报告。文件，就是每一棒交出去的接力棒。
>
> 有同学会问，那项目经理在哪里？在大型团队里，项目经理会负责排期、风险和跨团队协调。但今天是你亲自指挥六个 AI 岗位，所以项目推进暂时由你承担：你决定什么时候切换 `@岗位`，检查上一棒是否交齐，再允许下一棒开工。架构师也没有单独创建，因为第一周的小项目先由后端承担基础架构设计。我们讲清这两个职能，但不额外增加岗位，让小白先把主链走通。
>
> AI 时代并不是这些岗位都消失了，而是每个岗位都从“亲手制作更多东西”转向“定义规则、指挥生成、检查证据并承担责任”。产品经理不再以文档字数证明价值，UI 不再以画了多少页面证明价值，前后端不再以手写多少行代码证明价值，测试和运维也不再以重复操作多少次证明价值。真正值钱的是判断和闭环。
>
> 现在请你拿一张纸画出六个方框，用箭头连起来，并在每条箭头上写文件名。能画出来，说明你以后换任何 AI 工具都不会迷路。带走一句话：工具只是工作台，岗位、交接物和验收闭环才是软件工程。下一节，我们就在 TRAE 里把这六个岗位真正建出来。

## 常见懵点（导师备用）

- “为什么没有独立架构师” → 第一周小项目由后端承担基础架构设计，先减少角色负担；
- “为什么测试不能直接修代码” → 发现问题和修复问题要保留责任边界，才能复测和追踪；
- “所有岗位都能由一个 Agent 做吗” → 技术上可以，但课程刻意拆岗，让学员看清工程流程和交接责任。
