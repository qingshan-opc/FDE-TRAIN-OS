# 第 6 节 · UI 复验与后端交接

## 本节目标

- 让 UI 对照原设计复验，而不是让前端自己验收自己；
- 让前端按 UI 问题清单修复并回到 UI 复验；
- 生成后端能读懂的 `frontend-api-needs.md`；
- 切换 `@后端` 完成接收，但不提前开发 Day3 内容。

## 第一次切换：前端 → UI

UI 读取 `design-spec.md`、`ui-flow.md` 和 `frontend/` 三个文件。每项输出：

- 通过或不通过；
- 对应文件依据；
- 可量化差距；
- 责任岗位。

UI 不直接修改前端代码。模糊的“还原度不够”也不合格，应写成具体颜色、字号、间距、布局或交互差距。

## 第二次切换：UI → 前端 → UI

前端只处理 UI 的问题清单，说明修改文件和复测方法。完成后学员再次切回 UI 复验，直到全部通过。

## 第三次交付：frontend-api-needs.md

由前端根据已经通过的页面整理：

| 内容 | 示例 |
|---|---|
| 页面需要展示的数据 | 名称、金额、状态、更新时间 |
| 用户提交的内容 | 筛选条件、表单字段 |
| 期待后端返回 | 数据列表、总数、处理结果 |
| 异常怎样展示 | 错误文案、重试按钮、保留输入 |

不要编造接口地址、数据库结构或密钥。这是数据需求，不是后端已经承诺的接口合同。

## 第四次切换：前端 → 后端

`@后端` 只读取 `PRD.md` 和 `frontend-api-needs.md`，复述收到的业务规则、页面数据和待确认问题。今天不让后端提前开发，Day3 再正式开始。

## 口播稿

同学们好，我是你们的老师404。前端页面能运行后，还差最后一条交接链。先切回 @UI，让设计岗位对照 design-spec 和 ui-flow 复验。前端不能自己给自己的还原度打满分。

UI 的反馈也必须可执行。不要说“高级一点”，而要说哪种颜色、多少像素、哪个状态、哪条流程不一致。然后切回 @前端修复，再回 @UI 复验。这是今天第二个完整闭环。

页面通过以后，让前端生成 frontend-api-needs.md。它要告诉后端每个页面需要哪些字段，用户会提交什么，期待返回什么，失败时页面怎样提示。但前端不能自己编接口地址，更不能把密钥写进去。

最后切换到 @后端，只让它读取和复述，暂时不要开发。这样你能确认交接是否完整，也把 Day3 的开工点停在一个清楚的位置。今天你完成的是 UI 到前端，再回 UI，最后交给后端的真实岗位接力。同学们，本节先到这里。
