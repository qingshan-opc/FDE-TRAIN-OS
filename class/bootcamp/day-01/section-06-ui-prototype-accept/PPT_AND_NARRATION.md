## 02 · ui-shift

**PPT（屏幕）**
- UI · 传统 vs AI 时代
- 传统：线框 · 视觉稿 · 调色 · 组件
- 现在：信息层级 · 操作路径 · 设计约束

**口播**
> 先回顾 UI 的变化。传统 UI 会花大量时间画线框、做视觉稿、调整颜色和组件；AI 时代，原型可以快速生成，UI 更重要的职责是信息层级、操作路径和设计约束。用户第一眼看什么，最常用操作在哪里，加载、空数据和错误时怎么办，这些判断不能只靠一句“做得高级一点”。

文稿：`video/scripts/narration/02-ui-shift.txt`

## 03 · read-repeat

**PPT（屏幕）**
- 第一段：先读 PRD，暂不生成
- 用 5 句话复述
- 用户 · 问题 · 操作 · 页面 · 验收
- 读不到文件就先停下检查

**口播**
> 切到 UI 后，第一句话不是“帮我生成页面”，而是“请读取 PRD 文件，先用五句话复述需求”。要求它说清目标用户、核心问题、主要操作、页面范围和验收标准，然后停下来等你确认。如果它读不到文件，就不要让它猜，先检查文件是否在工作区根目录。为什么要复述？因为文件交接成功不等于理解成功。五句话复述能用最低成本发现偏差。理解不一致时，先改理解，不要急着生成。

文稿：`video/scripts/narration/03-read-repeat.txt`

## 04 · design-interview

**PPT（屏幕）**
- 第二段：逐题确认设计
- 设备 → 首页重点 → 风格 → 主色 → 常用操作
- 每次只问 1 题，并给推荐理由

**口播**
> 你确认需求理解一致后，再让 UI 一次只问一个设计问题。先问主要使用设备，再问首页最重要的信息，然后是页面风格、主色、最常用操作，以及加载、空数据和错误状态。每题让它给一个推荐答案和理由，但最终选择由你做。你不是在考色彩理论，而是在确认设计是否适合真实工作场景。

文稿：`video/scripts/narration/04-design-interview.txt`

## 05 · real-states

**PPT（屏幕）**
- 三个真实状态不能漏
- 加载中 · 告诉用户正在处理
- 空数据 · 解释原因与下一步
- 错误 · 诚实提示，不留白屏

**口播**
> 这里要特别关注三种容易被忽略的状态。第一，加载中：数据还没回来，页面告诉用户正在处理；第二，空数据：没有结果时解释为什么为空、下一步能做什么；第三，错误状态：接口失败时诚实提示，而不是留一块白屏。AI 很容易生成一张只有理想数据的漂亮页面，成熟 UI 要考虑真实世界不顺利的时候。

文稿：`video/scripts/narration/05-real-states.txt`

## 06 · page-plan

**PPT（屏幕）**
- 第三段：先确认页面方案
- 页面结构 + 用户操作路径
- 对照 PRD：不遗漏、不擅自增加
- 通过后回复：确认页面方案

**口播**
> 问题完成后，先让 UI 展示页面结构和用户操作路径。比如首页有四个区块，点击异常费用进入详情，再按部门筛选。此时仍不要生成最终原型。你要拿 PRD 文件对照：每个核心功能有没有页面承载，有没有多出未确认功能，用户能不能走完最重要的一条流程。确认后回复“确认页面方案”。

文稿：`video/scripts/narration/06-page-plan.txt`

## 07 · generate-files

**PPT（屏幕）**
- 第四段：生成 UI 交付物
- design-spec.md
- ui-flow.md
- ui-prototype.html
- 只用演示数据，亲手打开点击

**口播**
> 页面方案通过后，要求 UI 生成三个文件：design-spec 文件、ui-flow 文件和 ui-prototype 网页文件。原型使用演示或脱敏数据，不连接真实后端。生成结束后，在工作区找到网页文件并直接打开。不要只看 AI 的文字说明，要亲手点击按钮、切换筛选项、观察是否有反馈。

文稿：`video/scripts/narration/07-generate-files.txt`

## 08 · return-pm

**PPT（屏幕）**
- 第五段：切回 @产品经理验收
- 读取 PRD + 设计规范 + 流程 + 原型
- 逐项输出：通过/不通过 · 原需求 · 责任岗位
- 产品经理只检查，不直接改 UI

**口播**
> 传统的软件团队里，UI 可能把设计稿发给产品经理评审；AI 时代速度更快，但评审不能省。现在请你从 @UI 切换回 @产品经理。我们不是让 UI 自己说“我做得很好”，而是让最初确认需求的岗位拿着同一份 PRD 做业务验收。给产品经理的任务要非常明确：读取 PRD、设计规范、交互流程和原型，逐项输出“通过或不通过、对应哪条原始需求、责任岗位是谁”。要求它只检查，不直接修改 UI 文件。

文稿：`video/scripts/narration/08-return-pm.txt`

---

## 09 · fix-retest

**PPT（屏幕）**
- 不通过就回责任岗位
- @产品经理 发现问题
- @UI 按问题清单修改
- @产品经理 再次复验

**口播**
> 假设产品经理指出“招聘超期岗位没有红色提醒”，PRD 里明确要求超过七天标红。你就切回 @UI，只把这一条问题和 PRD 依据交给它修改。修改完成，再回 @产品经理复验。这个往返可能看起来麻烦，但它建立了真实的软件责任链：谁发现、谁修改、谁复验，都能说清。

文稿：`video/scripts/narration/09-fix-retest.txt`

## 11 · close

**PPT（屏幕）**
- 第一天完成的跨越
- 专业问题 → 产品需求 → UI 体验 → 产品验收
- 五问：谁 · 上游 · 交付 · 下游 · 验收
- 你正在指挥 AI 团队

**口播**
> 今天到这里，你已经完成了一个非常重要的跨越。你可能一开始还觉得软件开发是一堵代码墙，现在你已经知道项目从专业问题开始，产品经理把问题变成需求，UI 把需求变成体验，结果还要回到需求负责人验收。后续前端、后端、测试和运维会把这个原型逐步变成真实系统，但工程结构今天已经在你脑子里建立起来了。最后带走一句话：工具可以换，模型可以换，软件工程的岗位、交接物和验收闭环不会消失。以后面对任何 AI 开发工具，先问当前是谁、上游文件是什么、这一步交付什么、下一步给谁、谁来验收。能回答这五个问题，你就不再是被 AI 牵着走的小白，而是在指挥 AI 团队的领域项目负责人。同学们，本节先到这里。

文稿：`video/scripts/narration/11-close.txt`
