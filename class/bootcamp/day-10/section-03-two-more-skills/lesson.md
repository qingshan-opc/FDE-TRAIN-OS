# 第 3 节 · 再封装两个技能包（25′ · 实战）

> 🎬 视频位（现阶段：口播稿）
> 工具表扩编：1 件变 3 件。D7 的全流程提速复用——这次每件 15 分钟。

## 教学目标

- 按串联图把缺的两件 Skill 封装出来：说明书 + 边界声明 + 工具描述；
- 体验「流程复用的加速度」：第二三件比第一件快一倍——这就是方法沉淀的红利；
- 特别注意数据流对齐：上下游契约咬合。

## 流程安排（30′）

| 时段 | 内容 |
|------|------|
| 0–3′ | 分工确认：两件 Skill 各 13′，最后 4′ 数据流对齐检查 |
| 3–16′ | Skill #2：倒序写法（输出→验收→输入→步骤）+ 边界声明 + 工具描述 |
| 16–29′ | Skill #3：同上（发送/通知类 Skill 必须有「等确认」设计） |
| 29–30′ | 数据流对齐三查（见下） |

## 写作要点（与 D7 的差异）

1. **提速但别省件**：四部件 + 边界声明 + 工具描述，一样不能少；快在「你已经会了」，不是快在「跳过」；
2. **输入写明上游**：`输入：Skill A 的输出 JSON（含 kpi/exceptions 数组）`——契约咬合靠这一句；
3. **发送类 Skill 的特殊设计**（如果你的 #3 是发送/通知）：
   - 步骤第一步必须是「等待人工确认结果」；
   - 边界声明加「未收到批准时：不执行，保持等待」；
   - 工具描述的「何时用」写明「仅在人工确认通过后」。

## 数据流对齐三查（4′）

```
① A 的输出字段 ⊇ B 的输入要求？
② B 的输出（草稿）包含确认界面需要的信息吗（关键数字/风险标红）？
③ C 的输入（确认后的草稿+批准记录）从哪来？
```

## 🎬 口播稿（约 5 段 · 待审）

> 同学们，扩编开始。工具表从一件变三件，每件大概十三分钟。流程你们熟：倒序写、四部件、边界声明、工具描述——快在你已经会了，不是快在跳过部件，方法沉淀的红利就在这儿，对吧。
> 两个新要点。第一，输入段写明上游——比如输入：Skill A 的输出 JSON，含 kpi 和 exceptions 数组。契约咬合就靠这一句，别写一些数据这种模糊话。咱们流水线最怕接口对不齐。
> 第二，如果第三件是发送或通知类 Skill，步骤第一步必须是等待人工确认结果。边界里写死：未收到批准时，不执行，保持等待。工具描述的何时用也要写明——仅在人工确认通过后，对吧。
> 最后四分钟做数据流对齐三查。A 的输出字段能不能喂饱 B？B 的草稿里有没有确认界面要的关键数字和风险标红？C 的输入从哪来——确认后的草稿加批准记录。查不到咬合点，第四节编排必卡，咱们别留坑，对吧。
> 写不完两件也别硬撑：优先保证发送类那件，闸的训练价值最高。想封装的和串联图不一样？现在二选一，改图或改 Skill，图纸和施工必须一致。带走一句——三件齐了，咱们下一节真正串联，对吧。


## 常见懵点

- 「两件都要跑注入测试吗？」→ 今天时间关系：每件跑 1 条最关键的坏输入（空数据）即可；完整注入列入 backlog；
- 「想封装的和串联图不完全一样怎么办？」→ 改图 or 改 Skill，二选一现在定——图纸和施工必须一致；
- 「写不完两件？」→ 优先保证「发送类」那件（闸的训练价值最高）；另一件可简化步骤数。
