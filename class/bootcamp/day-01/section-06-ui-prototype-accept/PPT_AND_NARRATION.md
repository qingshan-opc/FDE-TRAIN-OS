## 02 · ui-shift

**PPT（屏幕）**
- UI · 传统 vs AI 时代
- 传统：线框 · 视觉稿 · 调色 · 组件
- 现在：信息层级 · 操作路径 · 设计约束

**口播**
> 传统 UI 花大量时间画线框、做视觉稿、调颜色和组件；AI 时代，原型可以飞快生成，UI 更重的担子是信息层级、操作路径和设计约束。用户第一眼看什么，最常用的操作放哪儿，加载、空数据、出错时怎么办——这些判断，靠一句“做得高级一点”可出不来。那切到 UI 以后，第一句话说什么？

文稿：`video/scripts/narration/02-ui-shift.txt`

## 03 · read-repeat

**PPT（屏幕）**
- 第一段：先读 PRD，暂不生成
- 用 5 句话复述
- 用户 · 问题 · 操作 · 页面 · 验收
- 读不到文件就先停下检查

**口播**
> 切到 @UI 后，记住，第一句话不是“帮我生成页面”，而是“请读取 PRD 文件，先用五句话复述需求”。让它说清目标用户、核心问题、主要操作、页面范围和验收标准，说完停下，等你确认。要是它读不到文件，别让它猜，先检查文件是不是在工作区根目录。为什么要复述？文件交接成功，不等于理解成功。五句话复述，能用最低成本发现偏差。理解不一致，先改理解，别急着生成。理解对齐了，才进入设计问答。

文稿：`video/scripts/narration/03-read-repeat.txt`

## 04 · design-interview

**PPT（屏幕）**
- 第二段：逐题确认设计
- 设备 → 首页重点 → 风格 → 主色 → 常用操作
- 每次只问 1 题，并给推荐理由

**口播**
> 你确认理解一致后，再让 UI 一次只问一个设计问题。先问主要用哪个设备，再问首页最重要的信息，然后是页面风格、主色、最常用操作，还有加载、空数据和错误状态。每题让它给一个推荐答案加理由，但拍板的是你。你不是在考色彩理论，是在确认设计适不适合真实工作场景。有三种状态，特别容易被漏掉。

文稿：`video/scripts/narration/04-design-interview.txt`

## 05 · real-states

**PPT（屏幕）**
- 三个真实状态不能漏
- 加载中 · 告诉用户正在处理
- 空数据 · 解释原因与下一步
- 错误 · 诚实提示，不留白屏

**口播**
> 哪三种？第一，加载中：数据还没回来，页面得告诉用户正在处理；第二，空数据：没结果时解释为什么空、下一步能干嘛；第三，错误状态：接口失败就诚实提示，别留一块白屏。AI 特别容易生成一张只有理想数据的漂亮页面，成熟的 UI 得考虑真实世界不顺利的时候。状态说清了，再看页面方案。

文稿：`video/scripts/narration/05-real-states.txt`

## 06 · page-plan

**PPT（屏幕）**
- 第三段：先确认页面方案
- 页面结构 + 用户操作路径
- 对照 PRD：不遗漏、不擅自增加
- 通过后回复：确认页面方案

**口播**
> 设计问题问完，先让 UI 展示页面结构和用户操作路径。比如首页四个区块，点异常费用进详情，再按部门筛选。这时候还不要生成最终原型。你拿 PRD 对着看：每个核心功能有没有页面接着，有没有多出没确认的功能，用户能不能走完最重要的那条流程。都没问题，回复“确认页面方案”。方案过了，才生成文件。

文稿：`video/scripts/narration/06-page-plan.txt`

## 07 · generate-files

**PPT（屏幕）**
- 第四段：生成 UI 交付物
- design-spec.md
- ui-flow.md
- ui-prototype.html
- 只用演示数据，亲手打开点击

**口播**
> 页面方案通过后，让 UI 生成三个文件：design-spec 文件、ui-flow 文件和 ui-prototype 网页文件。原型用演示或脱敏数据，不连真实后端。生成完，在工作区找到那个网页文件，直接打开。别只看 AI 的文字说明，要亲手点按钮、切换筛选项、看看有没有反馈。点完了，该谁出场了？

文稿：`video/scripts/narration/07-generate-files.txt`

## 08 · return-pm

**PPT（屏幕）**
- 第五段：切回 @产品经理验收
- 读取 PRD + 设计规范 + 流程 + 原型
- 逐项输出：通过/不通过 · 原需求 · 责任岗位
- 产品经理只检查，不直接改 UI

**口播**
> 传统软件团队里，UI 会把设计稿发给产品经理评审；AI 时代速度快了，但评审不能省。现在，请你从 @UI 切回 @产品经理。咱们不是让 UI 自己说“我做得很好”，而是让最初确认需求的岗位，拿着同一份 PRD 做业务验收。给产品经理的任务要明确：读取 PRD、设计规范、交互流程和原型，逐项输出“通过或不通过、对应哪条原始需求、责任岗位是谁”。记住，它只检查，不直接改 UI 文件。查出问题怎么办？

文稿：`video/scripts/narration/08-return-pm.txt`

## 09 · fix-retest

**PPT（屏幕）**
- 不通过就回责任岗位
- @产品经理 发现问题
- @UI 按问题清单修改
- @产品经理 再次复验

**口播**
> 举个例子，产品经理指出“招聘超期岗位没有红色提醒”，而 PRD 里明确写了超过七天标红。你就切回 @UI，只把这一条问题和 PRD 依据交给它改。改完，再回 @产品经理复验。这个往返看着麻烦，但它建了一条真实的软件责任链：谁发现、谁修改、谁复验，都说得清。全部通过了，留个记录。

文稿：`video/scripts/narration/09-fix-retest.txt`

## 11 · close

**PPT（屏幕）**
- 第一天完成的跨越
- 专业问题 → 产品需求 → UI 体验 → 产品验收
- 五问：谁 · 上游 · 交付 · 下游 · 验收
- 你正在指挥 AI 团队

**口播**
> 今天走到这儿，你已经完成了一个非常重要的跨越。早上你可能还觉得，软件开发是一堵代码墙；现在你知道了，项目从专业问题开始，产品经理把问题变成需求，UI 把需求变成体验，结果还要回到需求负责人验收。后面几天，前端、后端、测试和运维会把这个原型一步步变成真实系统，但工程结构，今天已经装进你脑子里了。最后带走一句话：工具可以换，模型可以换，软件工程的岗位、交接物和验收闭环不会消失。以后面对任何 AI 开发工具，先问五个问题：当前是谁、上游文件是什么、这一步交付什么、下一步给谁、谁来验收。答得出这五句，你就不再是被 AI 牵着走的小白，而是指挥 AI 团队的领域项目负责人。同学们，本节先到这里。
