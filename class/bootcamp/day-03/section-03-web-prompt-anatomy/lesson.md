# 第 3 节 · 解剖前端提示词：UI 先行，API 在后（15′ · 概念）

> 一句话：两份提示词、一条流水线——先出高保真原型，再接数据。

## 教学目标

- 用「四要素 + 两接口」的解剖法读 `Web_Client_Agent_Prompt.md` 与 `UIUX_Designer_Agent_Prompt.md`；
- 说清「UI 先行、API 在后」两阶段划分的原因：改界面成本低，改逻辑成本高；
- 掌握迭代指令的写法：具体、可量化。

## 讲授要点

### 两份提示词怎么接力

```
PRD.md（Day 1）──→ UIUX Designer Agent ──→ 高保真原型 + Design_Spec.md
                                                  ↓ 作为「视觉蓝本」
architecture.md（Day 2）──→ Web Client Agent ──→ 前端代码（先 UI 后 API）
```

- **UIUX Designer**：吃 PRD，产出高保真 HTML 原型和设计规范——它是「画脸的」；
- **Web Client**：吃原型 + 设计规范（主要输入），产出前端代码——它是「把脸变成真产品的」；
- 两份提示词的输入/输出接口恰好咬合：UIUX 的 Output Targets（`design/prototypes/`、`design/specs/Design_Spec.md`）正是 Web Client 的 Input Sources。

### 「UI 先行、API 在后」

Web Client 提示词把交付拆成两阶段：**阶段一只做 UI**（界面 + 无业务逻辑的基础交互），**阶段二才接 API**（状态管理、数据请求、完整业务流）。为什么？

- **改界面成本低，改逻辑成本高**：界面阶段改一处颜色是几分钟的事；一旦界面和业务逻辑缠在一起，改一处颜色可能牵动十处代码；
- **冻结易变的先冻结**：视觉是老板和同事最容易提意见的，先用原型收集完意见再写逻辑，返工最少；
- **可演示**：纯 UI 原型不依赖后端，随时双击就能给任何人看——今天你的 index.html 就是这个道理。

### 迭代指令：具体、可量化

Web Client 提示词里有一句要求协调者的话，你照着学：指令要「具体、精确」。

| 烂指令（AI 只能猜） | 好指令（AI 一次到位） |
|---|---|
| 标题大一点 | 标题字号从 24px 调到 32px |
| 颜色亮一点 | 主色从 #1D4ED8 换成 #2563EB |
| 按钮好看点 | 按钮圆角从 4px 改 8px，悬停时背景加深 10% |

配套口诀（工具包 README 里的）：**产出不对，先改约束再重生成，不要手改产物**——手改的产物，下次生成就被覆盖；改进提示词的约束，才永久生效。

## 🎬 口播稿（约 2.5 分钟）

【开场抛问】同学们，今天有两份提示词——设计的、前端的。为什么是两个，不是一个？这一节我们把它解剖开。

【接力】看流水线：「UIUX」吃你的 PRD，产出高保真原型；「Web Client」吃原型，产出前端代码。前一份的输出，正好是后一份的输入——这就是 Day 1 说的团队协作，只是执行者换成了 AI。

【两阶段】重点来了。Web Client 的提示词把活拆成两阶段：「UI 先行，API 在后」——先把界面做对，再接数据。为什么？因为「改界面成本低，改逻辑成本高」。界面上改个颜色几分钟；界面和逻辑缠在一起，改个颜色牵动十处。

【类比】像装修：先刷墙试色，不满意就重刷；你不会等家具全搬进去再试色——那时候动一面墙，全屋都得挪。

【迭代指令】还有一门手艺：下修改指令。烂指令是「标题大一点」，AI 只能猜；好指令是「标题字号从 24 调到 32」——「具体、可量化」，一次到位。记住口诀：产出不对，「改约束重生成」，别手改。

【带走的话】带走一句话——先冻结脸，再接心脏；改提示词，不改产物。

## 常见懵点（导师备用）

- 「UIUX 提示词要求生成多个界面文件，为什么今天我们只做一个 index.html？」→ 周报助手是单页产品，一个文件就够；提示词是通用模板，你作为协调者有权按 PRD 收窄范围——这正是「会判断」的体现；
- 「为什么不直接让 Web Client 一步把 UI + API 都做了？」→ Day 4 才学后端，今天没有 API 可接；即使没有这个课程安排，两阶段也是业界标准做法；
- 「我给的量化指令 AI 没照做怎么办？」→ 把该条指令加粗进约束重新生成；仍不照做，换更精确的表述（附上下文片段）再生成——迭代日志记一行。
