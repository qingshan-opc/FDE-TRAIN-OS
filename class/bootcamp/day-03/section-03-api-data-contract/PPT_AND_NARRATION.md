## 01 · open

**PPT（屏幕）**
- 先合同，后代码
- API_Spec.md
- DB_Schema.md
- 避免各写一套

**口播**
> 同学们好，我是你们的老师404。后端方案确认了，但咱们还是别急着生成服务。先定两份合同：接口合同，规定前后端怎么对话；数据合同，规定每条记录怎么保存。两份合同先对齐，后面才不会各写一套字段。先看接口合同要写什么。

文稿：`video/scripts/narration/01-open.txt`

## 02 · api-six

**PPT（屏幕）**
- 接口六要素
- 方法 · 路径 · 用途
- 请求
- 成功
- 错误

**口播**
> 一个完整接口，要写清六件事：请求方法和路径、用途、请求内容；成功结果要有状态码和返回示例，错误结果要写触发场景。只写一个地址可不够——前端得知道传什么，失败以后提示什么，也得明确。那第一份提示词怎么下？

文稿：`video/scripts/narration/02-api-six.txt`

---

## 03 · menu

**PPT（屏幕）**
- P1 · 先列接口菜单
- 只要 3—5 行
- 对应页面操作
- 确认后再展开

**口播**
> 第一段，只让后端列接口菜单。每行写方法和路径，再写一句用途和对应的页面操作，数量控制在三个到五个，先不展开参数和响应。你检查查询和提交有没有漏，确认了，回复“确认接口清单”。清单过了，才展开细节。

文稿：`video/scripts/narration/03-menu.txt`

---

## 04 · api-doc

**PPT（屏幕）**
- P2 · 生成 API 合同
- 每个接口写全
- 真实 JSON 示例
- 错误必须可触发

**口播**
> 第二段，生成接口合同。每个接口写全六个要素，成功响应给数据示例，错误响应说明触发条件。提醒一句：错误不能全写成五百——输入不合格通常返回四百，目标不存在通常返回四零四。接口说清了，再说数据。

文稿：`video/scripts/narration/04-api-doc.txt`

---

## 05 · db

**PPT（屏幕）**
- P3 · 最小数据合同
- 2—3 张表
- 字段与类型
- 每张表有主键

**口播**
> 第三段，生成数据合同。第一版只设计两张到三张表，每张表写明字段和类型、主键和必填规则，必要的数据关系也要说清。主键就像每条记录的唯一身份证——没有它，想准确查找和修改某条数据可就难了。两份合同都有了，对账。

文稿：`video/scripts/narration/05-db.txt`

## 06 · map

**PPT（屏幕）**
- P4 · 三方对账
- 页面操作
- 接口
- 表名.字段名
- 只列问题

**口播**
> 第四段，只对账，不修改。后端列出每个接口读或写哪些表字段，再把接口对应到页面操作。字段没来源，标不通过；表字段没人用，也标不通过；同一个意思出现两个名字，先列出来等你确认。对完账，才轮到你拍板。

文稿：`video/scripts/narration/06-map.txt`

## 07 · regenerate

**PPT（屏幕）**
- P5 · 完整重生成
- 不留半份旧合同
- 页面 → API → 数据表
- 一个最新版

**口播**
> 你确认修正方向，再发第五段：要求后端完整重生成两份合同，别只给几行补丁。最后输出从页面操作到接口、再从接口追到数据表的完整链路。两份合同只保留一个清晰的最新版，免得后面岗位拿错文件。这条链路长什么样？举个例子。

文稿：`video/scripts/narration/07-regenerate.txt`

## 08 · example

**PPT（屏幕）**
- 例：提交记录
- POST /api/records
- 201 创建成功
- records.id 与内容字段

**口播**
> 比如页面点击提交，对应一个创建记录的接口，请求内容必须带合同规定的字段。创建成功，返回二零一和新记录编号；缺必填内容，返回四百。后端再把记录写入数据表。看，一条完整链路，从头到尾都能检查。好，这一节收个尾。

文稿：`video/scripts/narration/08-example.txt`
