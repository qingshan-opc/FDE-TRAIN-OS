# 第 6 节 · 交接 UI 生成原型，再回产品经理验收（40′ · 交接实操）

> 一句话节引言：UI 不是自己想页面，产品经理也不是提完需求就离场；真正的闭环是“交接—设计—验收—修改—复验”。

## 教学目标

- 完成从 `@产品经理` 到 `@UI` 的手动交接；
- 让 UI 先复述需求、再逐题确认设计、最后生成原型；
- 回到 `@产品经理` 按 PRD 验收，并完成至少一次问题闭环。

## 三次岗位切换

```text
@产品经理完成 PRD
→ @UI 读取 PRD、设计并生成原型
→ @产品经理按 PRD 验收
→ 如不通过，@UI 修改
→ @产品经理复验
```

## UI 正式交付

- `design-spec.md`：颜色、字体、间距、组件和状态；
- `ui-flow.md`：页面、跳转和按钮行为；
- `ui-prototype.html`：使用演示数据、可直接打开和点击的交互原型。

## 产品经理验收格式

| 检查项 | 结果 | PRD 依据 | 责任岗位 |
|---|---|---|---|
| 目标用户与场景 | 通过/不通过 | 对应原文 | 产品经理或 UI |
| 页面与核心操作 | 通过/不通过 | 对应原文 | UI |
| 第一版范围 | 通过/不通过 | 对应原文 | 产品经理或 UI |
| 验收标准可见性 | 通过/不通过 | 对应原文 | UI |

## 🎬 口播稿（约 14 段 · 定稿）

> 同学们，来到 Day 1 最关键的一节。现在工作区已经有确认后的 `PRD.md`，产品经理这一棒完成了。接下来请你亲自点击当前岗位，切换到 `@UI`。这个动作不是换一个聊天风格，而是在做真实交接：上一个岗位把文件放在工作区，下一个岗位读取文件继续工作。
>
> 先回顾 UI 的变化。传统 UI 会花大量时间画线框、做视觉稿、调整颜色和组件；AI 时代，原型可以快速生成，UI 更重要的职责是信息层级、操作路径和设计约束。用户第一眼看什么，最常用操作在哪里，加载、空数据和错误时怎么办，这些判断不能只靠一句“做得高级一点”。
>
> 切到 UI 后，第一句话不是“帮我生成页面”，而是“请读取 `PRD.md`，先用五句话复述需求”。要求它说清目标用户、核心问题、主要操作、页面范围和验收标准，然后停下来等你确认。如果它读不到文件，就不要让它猜，先检查文件是否在工作区根目录。
>
> 为什么要复述？因为文件交接成功不等于理解成功。比如 PRD 写的是给财务负责人看预算异常，UI 可能误解成给普通员工报销；PRD 写的是电脑端看板，UI 可能默认做成手机应用。五句话复述能用最低成本发现偏差。理解不一致时，先改理解，不要急着生成。
>
> 你确认需求理解一致后，再让 UI 一次只问一个设计问题。先问主要使用设备，再问首页最重要的信息，然后是页面风格、主色、最常用操作，以及加载、空数据和错误状态。每题让它给一个推荐答案和理由，但最终选择由你做。你不是在考色彩理论，而是在确认设计是否适合真实工作场景。
>
> 这里要特别关注三种容易被忽略的状态。第一，加载中：数据还没回来，页面告诉用户正在处理；第二，空数据：没有结果时解释为什么为空、下一步能做什么；第三，错误状态：接口失败时诚实提示，而不是留一块白屏。AI 很容易生成一张只有理想数据的漂亮页面，成熟 UI 要考虑真实世界不顺利的时候。
>
> 问题完成后，先让 UI 展示页面结构和用户操作路径。比如首页有四个区块，点击异常费用进入详情，再按部门筛选。此时仍不要生成最终原型。你要拿 `PRD.md` 对照：每个核心功能有没有页面承载，有没有多出未确认功能，用户能不能走完最重要的一条流程。确认后回复“确认页面方案”。
>
> 页面方案通过后，要求 UI 生成三个文件：`design-spec.md`、`ui-flow.md` 和 `ui-prototype.html`。原型使用演示或脱敏数据，不连接真实后端。生成结束后，在工作区找到 HTML 文件并直接打开。不要只看 AI 的文字说明，要亲手点击按钮、切换筛选项、观察是否有反馈。
>
> 传统的软件团队里，UI 可能把设计稿发给产品经理评审；AI 时代速度更快，但评审不能省。现在请你从 `@UI` 切换回 `@产品经理`。注意，我们不是让 UI 自己说“我做得很好”，也不是让通用 Agent 随便点评，而是让最初确认需求的岗位拿着同一份 PRD 做业务验收。
>
> 给产品经理的任务要非常明确：读取 `PRD.md`、设计规范、交互流程和原型，逐项输出“通过或不通过、对应哪条原始需求、责任岗位是谁”。要求它只检查，不直接修改 UI 文件。产品经理发现页面少了一个功能，应把问题交回 UI；如果发现 PRD 本身遗漏了业务规则，才回到产品经理需求阶段补充并重新确认。
>
> 假设产品经理指出“招聘超期岗位没有红色提醒”，PRD 里明确要求超过七天标红。你就切回 `@UI`，只把这一条问题和 PRD 依据交给它修改。修改完成，再回 `@产品经理` 复验。这个往返可能看起来麻烦，但它建立了真实的软件责任链：谁发现、谁修改、谁复验，都能说清。
>
> 全部通过后，创建 `day1-handoff-log.md`。写下三次切换：产品经理交付了什么给 UI，UI 交付了什么，产品经理最终验收结果是什么；如果发生过修改，再写一行问题和复验结果。这份日志不是形式主义，它证明你已经亲自走过一次岗位协作，而不是只看 AI 在一个窗口里自说自话。
>
> 今天到这里，你已经完成了一个非常重要的跨越。早上你可能还觉得软件开发是一堵代码墙，现在你已经知道项目从专业问题开始，产品经理把问题变成需求，UI 把需求变成体验，结果还要回到需求负责人验收。后续前端、后端、测试和运维会把这个原型逐步变成真实系统，但工程结构今天已经在你脑子里建立起来了。
>
> 最后带走一句话：工具可以换，模型可以换，软件工程的岗位、交接物和验收闭环不会消失。以后面对任何 AI 开发工具，先问当前是谁、上游文件是什么、这一步交付什么、下一步给谁、谁来验收。能回答这五个问题，你就不再是被 AI 牵着走的小白，而是在指挥 AI 团队的领域项目负责人。

## 常见懵点（导师备用）

- “UI 直接生成了页面” → 退回到读取并复述 PRD，确认理解后再设计；
- “产品经理要求自己修改 UI 文件” → 拒绝越界，只输出问题和责任岗位；
- “原型打开后按钮没反应” → 回到 UI，按 `ui-flow.md` 补齐可见交互，再由产品经理复验；
- “是否算完整项目” → 今天完成需求和交互原型闭环，后续岗位继续实现、接数、测试和部署。
